# 代码修改后总结

每次完成代码修改（一个文件、一个功能或一次修复）后，必须在交付说明中给出修改总结，说明**修改之后**系统发生的重要变化，不得只报「改完了」或罗列文件清单。

## 1. 总结时机

- 每次实质性代码修改完成后，随交付说明一起给出；一个任务多次修改时，至少每个交付节点做一次完整总结。
- 修改涉及多个文件/多个切片时，总结须覆盖全部改动，不能只挑一部分。

## 2. 必须覆盖的内容

- **数据流向变化**：本次修改后数据从哪里产生、经过哪些层/组件、最终到哪里消费；新增或移除的流转路径；字段/格式变更（新增字段、类型变化、序列化格式、存储结构等）。
- **架构变化**：新增/删除/重命名的模块、组件、服务、类；依赖关系变化（谁依赖谁、新增/移除依赖）；分层边界的调整；状态管理与生命周期变化。
- **接口与契约变化**：对外 API 签名、事件、回调、配置格式的变化；影响哪些调用方，调用方是否已同步更新。
- **关键行为变化**：核心逻辑、时序、并发模型、错误处理策略的变化。
- **潜在影响面**：哪些既有功能可能受影响，已验证什么、未验证什么。

## 3. 格式要求

- 简洁、结构化（分点或小标题），先结论后细节。
- 与本次修改无关的内容不写；未验证的推断须标注。
- 总结作为交付说明中的「本次修改影响」一节；修改很小（单文件小改）时可压缩为 2-3 行，但数据流向与架构变化（若有）不可省略。
